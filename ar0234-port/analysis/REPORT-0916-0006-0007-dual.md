### 1.2 0006 是**必要**的：反证实验

两条手臂的**历史完全相同**（先跑 1920x1200@30，让 3A 服务装载 `isp_param_3dnr.bin`、libisp 打开 D3D，
再切到 1920x1200@120）：

| `d3d_min_vblank_us` | 1200p120 结果 | `vi0` | dmesg |
|---|---|---|---|
| **0**（旧行为，互锁关闭） | **0 帧 / 12 s**，`timeouts=12` | `frame cnt 1, lost_cnt 1` | `frame lost` **482** 行 |
| **500**（0006 默认） | **1440 帧 / 12.003 s = 119.97 fps**，`>1.5x = 0` | `frame cnt 1441, lost_cnt 0, error_cnt 0` | `frame lost` **0** |

日志：`analysis/vfr/a45-il0.log`、`analysis/vfr/a45-il500.log`。恢复只需
`echo 500 > /sys/module/vin_v4l2/parameters/d3d_min_vblank_us`，**不需要重启**。

顺带量到一个 0006 的**能力边界**：互锁关闭时，`FRAME_LOST` 中断里的兜底逻辑
（`sunxi_isp.c`：`frame lost with 3DNR on, disabling 3DNR for this stream`）**救不回来**——
它只清 D3D_EN，不丢弃已经带 D3D/LBC 状态的 load image，流仍然是 0 帧。也就是说
**"开流前就决定"是必须的，"出事后补救"不够**。

### 1.3 阈值 500 µs 的依据

0006 用传感器时序自己算消隐：`vblank_us = 1e6 * (vts - height) / (fps * vts)`（不依赖线率假设，
ISP 一帧最多只能吃一行时间）。500 µs 的来历是实测：

| 模式 | vts | 消隐 | 3DNR | 实测 |
|---|---|---|---|---|
| 1920x1200@120 | 1220 | **136 µs** | off（0006） | ✅ 17861 帧 / 150 s / lost 0 |
| 1920x1200@120，互锁关闭 | 1220 | 136 µs | **on** | ❌ 每帧 FRAME_LOST，0 帧 |
| 1920x1200@110 | 1331 | 894 µs | on | ✅（源码注释记录，fll 1331 clean） |
| 1920x1080@126 | 1162 | 560 µs | **allowed** | ✅ 1250 帧 / 10 s，lost 0 |
| 1920x1080@120 | 1220 | 956 µs | allowed | ✅ 1200 帧 / 10 s，lost 0 |
| 1920x1080@132 | 1109 | 198 µs | off | ✅ 1056 帧 / 8 s，lost 0 |
| 1280x720@198 | 737 | 116 µs | off | ✅ 1588 帧 / 8 s，lost 0 |

即：**已知会坏的最高消隐 136 µs，已知能开 3DNR 的最低消隐 560 µs**，500 µs 落在
这个未被测量的空档里偏保守一侧。要把它收紧，需要在 1200p 上把 fps 从 110 扫到 122
（同时用固定参数强制 3DNR 打开，否则 3A 服务在 `fps > 110 && height >= 1200` 时会自动换
`isp_param_no3dnr.bin`）——这一步本轮**没做**，标为未做项（见 §6）。

### 1.4 1080p 默认 133 fps 的复核 —— **0006 覆盖不到，是另一个问题**

| 模式 | vts | 消隐 | 3DNR | 结果 |
|---|---|---|---|---|
| 1920x1080@120 | 1220 | 956 µs | allowed | ✅ 1200 帧 / 10 s，`lost_cnt 0` |
| 1920x1080@126 | 1162 | 560 µs | allowed | ✅ 1250 帧，`lost_cnt 0` |
| 1920x1080@130 | 1126 | 314 µs | off（互锁） | ✅ 1299 帧 / 10 s（`lost_cnt 1`，见下） |
| 1920x1080@131 | 1117 | 252 µs | off | ✅ 1048 帧，`lost_cnt 0` |
| 1920x1080@132 | 1109 | 198 µs | off | ✅ 1056 帧，`lost_cnt 0` |
| **1920x1080@133** | **1100** | **136 µs** | off | ❌ **3 帧 / 8 s**，`frame lost` + reset 各 **894** 行 |

133 fps 的失败**不是 D3D 造成的**：日志里 0006 已经把它判成 `3DNR off (limit 500 us)`
并真的清掉了 D3D_EN，仍然从第 4 帧起 `isp0 frame lost!` / `sunxi_isp_reset:isp0 reset!!!,
ISP frame number is 0` 无限循环（间隔约 17 ms，与 133 fps 无关）。而且消隐 136 µs
在 1200p120 / 720p198 上都能跑（116 µs 都能跑），所以"消隐不够"解释不了 1080p133。
失败点严格卡在 vts 1109（OK）与 vts 1100（坏）之间，1080p 的这个 vts 是驱动按 133 fps
算出来的最小值（`[ar0234_mipi]s_fmt set width = 1920, height = 1080, fll = 1100 (133 fps)`）。

⇒ 结论：**1080p 的实际可用上限是 132 fps**（0 丢帧），133 fps 是另一个未定性的缺陷
（怀疑在 AR0234 1080p 模式的最小 VTS / 传感器内部行时序，不在 ISP D3D 路径）。
对用户目标（1200p120）无影响。定性这一步还没做完，下一步见 §6。

另外一个观测：`@120` 请求时**实测 fps 会随开流时刻的 AE 状态在 119.07–120.04 之间浮动**
（A1 是 119.07，A2/A3 是 120.04），原因是传感器驱动按 `frame_rate` 控件的当前值算 FLL，
而 AE 的长曝光会拉长帧长（HANDOFF §3.10 记过同一现象）。两种情况下 `lost_cnt` 都是 0。

## 2. B：第二路物理相机 —— **通道未打通（已定性），路 1 零回归**

### 2.1 `isp01` 到底是独立 ISP 还是别名？——**同一块 ISP 硬件的虚拟实例**

四条独立证据：

1. **硬件只有一块 ISP**。`/sys/kernel/debug/mpp/vi` 头部自报硬件能力：
   `VIN hardware feature list: mcsi 3, ncsi 2, parser 3, isp 1, vipp 4, dma 6`
   —— `isp 1`。设备树里能注册出 `sunxi_isp.0` / `sunxi_isp.1`（本轮实测），但硬件只有一个。
2. **寄存器窗口互相覆盖**（板级 dtsi `sun60iw2p1.dtsi` 与内核树 `sun60i-a733-orangepi-zero3w.dts`）：
   ```
   isp00: reg = <0x05900000 0x1300>   -> [0x5900000, 0x5901300)
   isp01: reg = <0x058ffffc 0x1304>   -> [0x58ffffc, 0x5901300)
   isp02: reg = <0x058ffff8 0x1308>   -> [0x58ffff8, 0x5901300)
   isp03: reg = <0x058ffff4 0x130c>   -> [0x58ffff4, 0x5901300)
   ```
   四个窗口**结束地址完全相同**、大小随 id 每次 +4 —— 这是"同一块寄存器，用 id 区分"的
   厂商写法，不是四块独立 ISP。
3. **DT 明说**：`isp00 { work_mode = <0x0>; status = "okay"; }`，而
   `isp01/02/03 { work_mode = <0xff>; status = "disabled"; }`；板级 dts 里
   `&isp01/&isp02/&isp03` 还被显式 `status = "disabled"`（前面几行是注释掉的同一件事）。
4. **驱动代码**：`vin-isp/sunxi_isp.c` probe 里
   ```
   if (isp->id == isp_virtual_find_logic[isp->id]) { clamp work_mode } else
   if (isp->work_mode == 0xff) {
           logic_isp = glb_isp[isp_virtual_find_logic[isp->id]];
           if (logic_isp->work_mode == ISP_ONLINE) {
                   vin_log(..., "isp%d work in online mode, isp%d cannot to work!\n", ...);
                   isp->is_empty = 1;  goto init;      /* 不 iomap 寄存器 */
           }
   }
   ```
   即：**逻辑 ISP 一旦工作在网络(ONLINE)模式，同组的虚拟 ISP 一律被标成 empty**，
   连寄存器都不映射。

⇒ 所以 T9b 里"isp01（独立 ISP，参数文件互不干扰）"这句**是错的**。这块 SoC 上两路
4-lane 相机**不可能各有独立 ISP**；只能共用 ISP602，或其中一路走 bypass/RAW。
（diag 命令：`sudo cat /sys/kernel/debug/mpp/vi | head -6`、
`sudo fdtget /boot/dtb/.../zero3w.dtb /soc@3000000/vind@5800800/isp@58ffffc work_mode`）

### 2.2 第二路节点/实体现状（DTB **未改**时的基线）

`/sys/class/video4linux/*/name` 与 `media-ctl -d /dev/media0 -p`（`analysis/media0-dual.txt`）：

## 3. C：其余已知缺陷

### 3.1 probe 时 `v4l2 sub device scaler get_selection error!` —— 已定性，无害噪声

来源唯一：`vin-video/vin_video.c:1351` 的 `vidioc_g_selection()`，它把
`V4L2_SUBDEV_CALL(scaler, pad, get_selection, …)` 的负返回值直接打成 `vin_err`。
被调的 `vin-vipp/sunxi_scaler.c:sunxi_scaler_subdev_get_selection()` 只认
`V4L2_SEL_TGT_CROP_BOUNDS` 和 `V4L2_SEL_TGT_CROP`，**其他 target 一律 `return -EINVAL`**：

```c
	switch (sel->target) {
	case V4L2_SEL_TGT_CROP_BOUNDS: ...
	case V4L2_SEL_TGT_CROP:        sel->r = scaler->crop.request; break;
	default: return -EINVAL;                 /* <- 于是上层 vin_err 刷屏 */
	}
```

也就是说：**任何用 `VIDIOC_G_SELECTION` 问 `COMPOSE` 等目标的上层程序都会贡献一条错误日志**
（`v4l2-ctl --all`、libisp 都会）。本轮全新启动的 dmesg（`analysis/dmesg-boot-0007.txt`）
里这条是 **0 次**（之前在有多路/多进程反复开流的场景里出现过），属于无害噪声。
修法（未做）：`default` 分支返回 sink 的当前 rect（`scaler->formats[SCALER_PAD_SINK]`）而不是 -EINVAL。

### 3.2 IOMMU 空指针 DMA（`0x0 is not mapped` / `Bug is in CSI module, id:0x2`）—— 未解决

本轮**没有复现**，因为触发序列正是上一轮那个"两个 S_FMT 都先做"的双路顺序，
本轮没有再去跑它（那会把板子拖进 T14 里观察到的卡死态）。触发条件沿用上一轮的结论：
`vinc0` 与第二路同时做 S_FMT，**共享上行**被第二次 `vin_pipeline_try_format(vinc, set=true)`
改写（sensor 变 960x600 而 `scaler.0` 仍是 1920x1080），再去出流时 CSI 侧拿到 0 地址。
定性：与 §3.3 同一个坑的下游后果，**不是独立缺陷**。⛔ 优先级仍高（内核级 fault）。

### 3.3 S_FMT 顺序陷阱 —— 未修，约束写死在文档

`tools/dual_dtb.sh`/§2.3 的双路尝试里 `input 0: ` 为空这一现象说明第二路的 S_INPUT/S_FMT
一旦参与，整条共享上行的 ACTIVE format 就会被重设。**框架层没修**；当前约束是：
> 双路必须"先把主路开起来（S_FMT + STREAMON），再配副路"，且第一路出流期间不要再对
> 第二个节点做 S_FMT。

这条只写进了 HANDOFF §3（本轮更新），用户态没有强制手段——因为第二路目前根本出不了帧，

### 3.4 T16（重载后 ISP 坏）—— **分割定性：一个是 panic（已修 0007），一个是 DT 缺 reset**

本轮实测把 T16 拆成了三件互不相同的事：

**(a) `rmmod vin_v4l2` 根本做不到**（不是"坏了"，是内核不允许）：

```
$ sudo rmmod vin_v4l2

$ sudo rmmod vin_io

vin_io     61440  3    ar0234_mipi,vin_v4l2
```
`vin_v4l2 ↔ vin_io` 互相引用（循环 refcount），所以两个都卸载不掉。
"出流后 rmmod vin" 这个操作在这块板上**无法发生**。

**(b) 只重载传感器模块 → 内核 panic（0007 修的就是这个）**。串口日志原文
（`analysis/t14/serial-0006.log`，行 6013+，`analysis/t16.log` 是同一序列的 dmesg 侧）：

```

[ 2120.052132] T16-1789539302
```

触发条件就是"传感器 → mipi 的 media link 不存在"，而 `vin_create_media_links()` 只在 vin

```
input 0: sunxi-vin

S_FMT: Invalid argument

=== 7. board still up? ===
```

即 panic → 干净的 ioctl 失败。**遗留**：重载传感器模块之后 ISP 管线仍然是死的
（S_FMT 返回 EINVAL，恢复要重启）——这一半没修，原因见 (c)。

（`analysis/dmesg-boot-0007.txt`，**每次启动都出现**，不是重载才会有。）对应代码
`vin.c:256-259`：`devm_reset_control_get(dev, "isp_ret")` 失败 → 打 warning → 存 NULL。
而厂商 dtsi 里写的是：

```
resets = <&ccu RST_BUS_CSI>, <>;          /* <- 第二个 phandle 是空的占位 */

```
（`sun60iw2p1.dtsi:2588-2589`）。所以 `resets` 里只有 1 个有效 phandle，取 `"isp_ret"` 必然失败。
驱动对 NULL 是容忍的（`reset_control_*` 对 NULL 返回 0），ISP 自带的 `sunxi_isp_reset()`
仍然工作，**所以这是无害 warning**。修法：把 `RST_BUS_ISP` 之类的真实 reset 填进第二个 phandle
（需要 CCU 头文件确认编号），或保持现状。**这也说明"ISP 无法被硬复位"**——这正是 (b) 里
重载后救不回来的结构性原因。

### 3.5 T15（dmesg 噪声）—— 逐条定性

| 消息 | 出现条件 | 判断 |
|---|---|---|
| `ar0234_mipi is not used, video0 cannot be close!` | `vidioc_close` 时 `cap->pipe.sd[VIN_IND_SENSOR]` 非空而传感器没被真正绑定（如 §3.4(b) 重载后）。`vin_video.c` 的 close 分支本来还 `return -1`，会让 close 失败 | 无害但**掩盖真实原因**，建议改成 `vin_warn` + 不 return |

### 3.6 `ar0234-3ad` 的 per-ISP 会话 —— 未做，且**前提不成立**

`ar0234-3ad` 现在仍是"一路流 → isp0"的单会话（`userspace/src/isp3a.cpp`）。

所以"video1 → isp1 的 per-ISP 会话"**没有可实现的硬件基础**。
两路 4-lane 相机的现实接口方案只能是在同一个 isp0 上做多会话（依赖 T14 的
第二输出通道，目前出不了帧）。⇒ 建议把任务 T9b/T14 的目标改成
"共用 isp0 的两路时分/多通道输出"，per-ISP 的说法从 HANDOFF 里去掉。

## 5. 本轮额外发现的两个"文档/工具"缺陷（已修）

### 5.1 `patches/0005` 原来无法应用（且与部署模块不一致）

2. hunk 头声明 17/26 行，实际正文 16/25 行 —— `patch` 会越过 hunk 边界读到末尾的

```
checking file vin-video/vin_video.c
rc=2
patch: **** malformed patch at line 63: --
```

修法：保留提交信息原文，删掉伪 diffstat，**正文按两个真实文件状态重新生成**
（`pristine+0003` → `build/vin-d3d-lbc`，并剔除属于 0006 的那一个 hunk）。
修好后 `patch` 返回 0，且成为 §4.3 那条"逐字节一致"的一部分。

   用 `media-ctl -d /dev/media0 -p` 确认 link 是否 ENABLED、`prs_in` 的
   `y` 是否为 0（= CSI 一行都没进）。

8. 收尾：`tools/dual_dtb.sh disable`（或恢复 `.pre-second-cam`）→ 重启 →
   `tools/hwtest/vfrrun.sh final-single 120 …` 确认第一路仍然 lost_cnt=0。

**遗留风险**：

- `apply.sh` 现在会往**内核树**打 0005/0006（新增），而内核树是 root 属主且不该动；
  本轮**没有执行** `sudo bash apply.sh`。要走这条路请先确认。
