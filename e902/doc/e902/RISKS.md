# E902 风险与未决问题清单

日期：2026-09-22 · 依据：`doc/e902/RESOURCE-MAP.md`、`doc/e902/FINDINGS-LEDGER.md`

## A. 已确认的风险

| # | 风险 | 影响 | 现有缓解 | 等级 |
|---|---|---|---|---|
| A1 | Linux 侧无法重定位 E902 的 PC（无内核复位位） | 现有"借用核"方案整体不可用；必须走 bl31 | 已在本轮用 9 组实验证实，不再有人重复踩坑 | **高**（阻塞级） |
| A2 | 替换 `scp.fex` 会让 bl31 等待握手；无握手则板子起不来 | 板子不可启动，需物理恢复 | 有 `backup/sd-boot-head.img` + `restore-sd-auto.sh`；本轮未执行 | **高**（未执行） |
| A3 | 自己固件接管小核后失去 DRAM 变频 / suspend / PMIC 看护 | 性能下降；`echo mem` 醒不过来（要硬复位） | 全是软失败（SMC 返回错误码）；`AW_DMC_DEVFREQ` 可关掉以免每 100 ms 重试 | 中 |
| A4 | `PL_CFG0` 一个寄存器装 8 个脚，与 Linux 读改写竞争 | 最坏破坏 PL0/PL1（PMIC 的 I2C），可能伤硬件 | 只在初始化写一次、只动 PL2/PL3、读回校验；等 Linux 启动完再加载 | 中 |
| A5 | SRAM_A2 双地址（`0x40000000` 两侧含义不同） | 误用会静默破坏内核内存（`CONFIG_STRICT_DEVMEM` 未开） | 统一走 `awdevmem.py`，强制换算 + 越界拒绝 + 写回校验 | 中（已收敛） |
| A6 | ~~小核 `S_UART0` 没有引出到 TL101 的 USB-TTL~~ **已解决** | — | 板子 USB 上的 FT232H 就是 E902 控制台（板子自己的 `/dev/ttyUSB0`），线路已实测确认（翻转 PL2 时收到 10 字节，基线 0 字节）。见 `CONSOLE-CHANNEL.md` | ✅ 已消除 |
| A7 | `/dev/ttyUSB0`（CH340）在 `dmesg` 里反复 disconnect/reconnect | 串口控制台可能中途掉线 | 优先走 ssh 上板；串口仅作备用 | 低 |

## B. 未决问题（需要更多证据）

| # | 问题 | 现状 | 下一步怎么证实 |
|---|---|---|---|
| B1 | bl31 与小核的**握手协议**长什么样 | 未知；旧笔记只记录"换 scp.fex 后无握手、板子起不来" | 反汇编 `scp.fex` 前若干条指令 + 读 `arisc_i.h` 的 `dts_cfg_64`；用 `min2` 式探针逐步逼近 |
| B2 | 小核收中断到底是不是 48 | 手册写明 48 = "CPUX MSGBOX WRITE IRQ FOR CPUS/RISCV"，**代码用 48 是对的**；但硬件上从未真的触发 | 固件真正跑起来后读心跳里的 `mbox_irq` 计数 |
| B3 | `S_SPI` 的真实 `S_SPI_CLK` 频率（M/N 取值） | 手册给了寄存器布局与父时钟表；固件按 pll-ref/1 计算（本板 DCXO=26 MHz，勿用 dcxo mux 0，T31/T34） | 读 `0x070150` 实际值 + 用示波器/逻辑分析仪量 SCLK |
| B4 | 中断响应延迟（IRQ 29/38/48） | 无数据；**但控制台通道已就绪，可直接取证** | 固件内用 S_TIMER 打时间戳，统计 min/max/抖动 |
| B5 | 排针上 `S_SPI` 的 MOSI/MISO/CLK/CS 具体是哪几个 pin | 未查到明确复用组（dtsi 里 `r_spi` 没有 pinctrl 组） | 查原理图 Sheet 与 `pinctrl-sun60iw2-r.c` 的 PL/PM 功能表 |
| B6 | 板子是否真的从"唯一可启动介质"启动（SD 还是 eMMC） | 未确认 | 板上 `lsblk` / `cat /proc/cmdline` / 看 boot0 来源 |
| B7 | 旧的 `HANDOFF-RT-IMAGE.md` 说"E902 卡在 SCP 参数块协议"是否与本轮 F6 一致 | 一致：都是"bl31 那条路没握手" | 交叉核对旧笔记的原始日志 |

## C. 依赖厂商文档/固件的结论（可能随版本变化）

- 中断号（表 12-2）、寄存器位定义（4.2.5.x）、`E902_CFG` 清单（5.2.3）都来自
  `A733_User Manual_V0.91.pdf`（2024-12 版）。换手册版本需复核。
- 复位释放由 bl31（闭源）完成，行为无法从源码确认：`monitor.fex` 不在工程里。
- `scp.fex` 的实际行为来自反汇编推断（DESIGN-NOTES §3），不是厂商文档。

## D. 本轮明确**没有**做的事（避免误读）

- 没有改动/刷写任何启动介质、u-boot、`scp.fex`。
- 没有改内核配置或重新编内核（本轮只读内核树）。
- 没有在硬件上真正跑到"中断触发"和"SPI 读取"这两条验收项（原因见 A1，非本实现缺陷）。
- 没有把改动提交到上游或官方 SDK 主干。
| B8 | `0x40000000..0x40004000` 这 16K（镜像下方）为何每 0x100 有一个 `0x15` 字节 | 未解释；无已知使用者 | 多次读确认稳定性、与编译器/上电顺序对照，或查厂商 SRAM 初始化文档 |
| B9 | `S_MBOX` 通道 0 里为何在实验前就有 1 条未被取走的消息 | 未解释；疑为启动阶段 bl31↔SCP 的遗留 | 复位前后对比、或从 scp.fex 的 ch0 使用点反查 |
