## 2. 最重要的事实（都实测过）

1. **软件侧没有 E902 内核复位位** —— 手册 4.2.5.24 / 5.2.3 与 `ccu-sun60iw2-r.c:221-234` 三方一致；
   `RISCV_BGR` bit0 只是**时钟门控**，写 1 是"从原地续跑"，PC 不重定位。
2. **逐级汇编探针证明内核从未从我们设的向量取指**（T9）：156 字节的 `min3`，第一条指令就写 SRAM，
   连标记都没出现。
3. **唯一路径是 bl31**：`bootm.c:409` 的 `ARM_SVC_ARISC_STARTUP = 0x8000ff10`，
   bl31 载入 → 设向量 → 放复位 → **等小核报就绪**（`arm_svc_arisc_wait_ready`）。
4. **握手协议已解出**（T15/T21）：mailbox **通道 3**，报文 `[u32 头][u32 字数][数据…]`；
   启动反馈 = 头 **0x00900200** / 13 个字（与厂商逐字节一致；注意 T22：此前两次启动失败
   的真因是 boot0 的 add_sum 包校验，不是 bl31 拒绝握手，hdr 值尚未被硬件验证过）。
5. **`scp.fex` 在介质上的位置已确认**（T17）：启动包 `@0x1004000`，`scp` 条 =
   rel `0x137C00` / size `0x19DB8` → **绝对 `0x113BC00`**；该处内容与工程里 `scp.fex` 逐字节相同。

## 3. 现在差什么（唯一剩余动作）

```bash
# 1) 送镜像到板子（TL101 上）
# 卡已在本轮刷好（读卡器路径）；如需板上重刷：cat e902/fw-out/scp-ours-padded-105912.bin | <ssh_board.sh> 'cat > ~/e902v2/scp-ours-padded.bin'
# 2) 写入（脚本自带尺寸/哈希/读回三重校验，需手输 YES）
<ssh_board.sh> 'printf "orangepi\n" | sudo -S sh ~/e902v2/flash-scp.sh ~/e902v2/scp-ours-padded.bin /dev/mmcblk1'
# 3) 重启并盯小核控制台
<ssh_board.sh> 'sudo reboot'   # 然后读板子的 /dev/ttyUSB0
```

**期望**：板子 `/dev/ttyUSB0` 出现 `=== A733 E902 firmware v2 ===` 横幅 +
`startup feedback (ch3 hdr=0x00900200 13w) : sent`。

**回滚**（板子能启动时随时可做）：
```bash
<ssh_board.sh> 'printf "orangepi\n" | sudo -S sh ~/e902v2/restore-scp.sh ~/e902v2/scp.fex /dev/mmcblk1'
```
若板子起不来 → 读卡器写回 `e902/backup/sd-boot-head-20260922.img`。

## 6. 已知残留

- `S_MBOX` 通道 3 的 RX 队列里有 **6 个字**（本次实验留下，构成两个格式合法的 `cmd=0x61` 包）。
  厂商 SCP 空闲不读它，ARM 也清不掉（FIFO 读端口属 CPUS）。清除方式：复位 `S_MBOX_BGR` 或重启。评估无害。
- `S_MBOX` 通道 0 里**在我们动手之前**就有 1 条未取走的消息（待查项 B9）。
- 旧备份 `sd-boot-head.img`(665cd428…) 与介质现状(`114cd1f3…`)不一致，**不要用它回滚**。
