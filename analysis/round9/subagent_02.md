## 3. 最值得警惕的 3 条

**① 「每一级都跑通」= 块级能力，被读成了系统可用。**
同一批材料里同时存在：H.265@1200p120 直接失败、G2D 4:2:0 非位精确、"只 open 就 close" 刷 3 条内核 Error、5–10% 开流坏启动、T16b 仍能整路 0 帧、underflow 未根除。把这些放在"✅ 可用性总览"一句话下面，会让接手者以为**单相机最简用法稳了**——实际不是。**建议把总览拆成"逐块可用性" + "端到端可靠性（带已知失败率）"两张表。**

**② 订正出来的"精确规则"本身是错的（#6）。**
`frame_lost + sunxi_isp_reset 风暴` 这一个可见签名，在 1080p@136（能自愈）和 162 MHz 时钟饿死（救不回）两种情况下**完全一样**。现在写进 HANDOFF §3.2 / README 的"不用重启"规则会让人在**真正需要重启**的那类故障上白白重试到死。这条比原来的"一律重启"更危险，因为它看起来更"精确"。**必须按触发原因分档，写清"时钟被压/hblank_short 型救不回"。**

**③ G2D 的"位精确/差异字节数"是三次测量三组数字（#13）。**
213834（audit）≠ 136451（fix）≠ ~1.15M（g2d 原始输出的 full-range 相加），>8 的计数从"0"到"42533"到"843003"都有。**任何把某个固定字节数当指标的写法都是错的**；能落地的只有两条：*4:2:0 UVC blit 不位精确（机理：Y 钳 16 + 色度重采样）；要位精确走两次 Y8（但只在 dma_heap dst 上验过）*。

> 附带提醒（第 4 条，够不上"最警惕"但会造成返工）：**HANDOFF §1 与 §3.28c 已经内部打架**——§1 说模块是 0009、板子要断电，§3.28c 说模块是 0010+0011、板子健康（我在板上复核：0010+0011、健康）。接手者若只读 §1，会拿到错版本与错状态。
